Python interpreter vs. C static compile

Python source text:

	def five():
    return 5
print(five())

C source text:

	#include <stdio.h>
int five() {
  return 5;
}
int main(int argc, const char ** argv) {
  printf("%d\n", five());
}

Here is some intermediate code for the main part of the five.py code. The code the calls five() and prints its return value. I don't have the code for the five() function here. There is a bit of other stuff I've omitted to fit this on on slide.

The first instruction RESUME is there simply as a marker or indicator to Python 3.13's JIT routines that this is a good place to start collecting information at run time; and it is a good place for JITting to replace instructions starting here with machine instructions. JIT stand for "Just In Time" a form of dynamic compilation at runtime. In compiled languages though, of course this kind of thing doesn't happen.

After that, the function five() is getting dynamically linked into the main program using MAKE_FUNCTION. By doing this, it can subsequently call the function five. Since print is a builtin function, this kind of thing as already been done for that. And next, we call the functions five(), followed by a call to the function print().

One thing to note here is that all instructions have at most one operand. And some instructions, like PUSH_NULL and POP_TOP, do not have an operand. These instructions and many of the other instructions have input and output to an Python interpreter execution stack.

Python's intermediate instruction set is stack based.

Now let's compare with the bottom LLVM code. The first thing that is done is to allocate memory onto a call stack, and in doing this the memory alignment of 4 bytes or 8 bytes is specified.

This LLVM code is somewhat hardware independent. However, in a later phase of clang, it is turned turned into machine-specific code in ELF executable format. The ELF binary becomes the executable file that is run. In other words, you don't run the C source text but run this executable file which has which has hardware-specific code.

In Python though, the intermediate representation you see is saved to disk. You can run either the Python source code, or the bytecode representation of it.

In either case, what we show above is a text representation of the underlying structures. We have carved instructions out of a stream of bytes. We will show how that is done in Python next.
