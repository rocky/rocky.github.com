Towards understanding assembly

Description of instructions can be found at:
https://docs.python.org/3/library/dis.html#opcode-collections.
Make sure to select the version for the version of Python you want.

To recap, we've identified, Python bytecode in many of its different forms, and have, for the most part, seen an assembly listing of the instructions. Now it is time start understanding in more detail what those instructions do.

Unfortunately, Python is so ever changing, that even if I were to try to describe specific instructions as I've done partially here, those instructions might have morphed into something else by lunch time. Python has changed the stack order of call parameters from left to right to right to left, only to have that change again in the next release or a few releases later. Python used to claim that there was only one way to write code—the Python way. But in terms of implementation, clearly it hasn't figured things out yet.

So the best you can do is to read the opcode section of the Python language manual and make sure you get the version matched with what you need. Unsurprisingly, even the docs have bugs in them, since they often can't keep up with the changes.

Decompilation

Some Python decompilers:

  • uncompyle6, decompyle3, decompile-cfg
  • https://pylingual.io

When there is a decompiler for the specific flavor of Python bytecode, we can sometimes skip the process of trying to understand what a program does from assembly. A decompiler produces Python source text. It reverses what Python's compile() function does.

As I said before, using general-purpose binary analysis and machine code tools like Binary Ninja, Hex Rays, or Ghidra is not going to be of much help with Python bytecode. Here are some Python decompilers:

[DOWN uncompyle6, decompile3, decompile-cfg] 12.2 ⟶ 12.2

These are the decompilers I have worked on and developed. The core of their approach goes back to John Aycock who was probably looking for some application for his Earley parser system around 2000. It was turned into a full usable decompiler by Hartut Goebel.

This approach I call a grammar-based approach. It provides very good and understandable results, but it can require a lot of work to get right. Uncompyle6 stops at Python 3.8. decompile3 tries to clean up the 20-year old code base, but only handles Python 3.7 and 3.8 The latest incarnation, decompile-cfg, starts at 3.8 and goes to 3.10, but I haven't finished a grammar for this. It uses python control flow analysis to fix the plaguing problems of control-flow handling.

[DOWN to pylingual] 12.2 ⟶ 12.2

pylingual is the newest kid on the block. While it uses the same disassemblerthat I wrote, xdis. However, it replaces the grammar-based approach with a LLM. It is pretty good, but it still suffers from handling control flow properly.

[DOWN to pycdc] 12.2 ⟶ 12.2

pycdc is a decompiler written in C++. It aims its slingshot at the moon and tries to cover all versions of Python. However currently it is best around Python 3.3. As best as I can tell, the code is pretty ad hoc: it looks at bytecode and sort-of simulates parts of it using a call stack like x-python does, but also looks for patterns of instructions in the code. This approach I don't think scales to the more recent versions of Python.

[DOWN to unpy3] 12.2 ⟶ 12.2

There are other, mostly single-version decompilers based on a Python 3.3 written in Python. They use the Python dis module, so you can only decompile the version that of Python that is running the decompiler. The decompiler names vary, but generally start with "unpy."

I did. In this slide are some artifacts from two examples. I do this not to put down pycdc, but rather to show the difficulty of the problem, and also some issues you run into.

example1 contains a very early version of Python bytecode, version 1.5. What's going on is that pycdc cannot handle the Python 1.5's older code structure. pycdc reports Python 1.0, but really it is Python 1.5, and Python 1.0's code type is different from Python 1.5's code type.

In xdis which is what my decompilers use, there are 7 code types defined. And this isn't enough. There are between two to four more variations needed to cover JVM-based Python, and possibly Python 3.15 when that comes out.
